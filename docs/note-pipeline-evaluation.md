# ノート品質の比較評価（R-22 / A-23 / T-29）

第1段階の評価セットは`tests/fixtures/note_pipeline.json`。本プロジェクトで作成した架空の講義で、教材から転記していない。原文、手作業の期待事項、期待台帳、期待ノート、意図的な劣化操作を含む。

期待事項は生成モデルの抽出結果とは独立に定めた。入力・初期値、初回表示・比較条件、退避・更新順、停止・出力、通常例と無反復例、説明を保持した不明名称の留保の6項目を比較する。フィラーだけを除外する。同時刻の2発話も別IDで追える。

## オフライン評価

`python -m unittest discover -s tests -v`で正常な台帳・本文の解析と表示、ID未掲載の拒否、意図的な意味劣化を構造検査だけでは拒否できないこと、独立照合でmajorを返した場合の保存拒否と修正上限を確認する。API応答は固定モックであり、モデルが欠落を発見できた証拠ではない。

台帳の原文網羅は「全IDが処理された」だけを示す。1つの発話のうち重要な条件だけを落とした抽出、誤った除外理由、本文にfact_idsを付けただけの意味欠落は原文との独立照合と人手評価が必要。

## 実APIでの比較（未実施・別途承認後）

1. 同じ架空原文と同じモデルで通常方式、`--quality-check`、`--note-pipeline`を別の出力フォルダへ生成する。入力・モデル・プロンプト版・コミット・日時を評価表へ記す。実教材を使う場合は権利を確認し、原文やノートをリポジトリへ追加しない。
2. 各方式を複数回実行し、原文の6期待事項を人手で「保持/一部欠落/欠落/意味変更」に分類する。完全保持数/6を記録し、不明名称の断定・創作を別に数える。短縮率を品質得点にしない。
3. 劣化例の各操作を期待ノートへ適用し、原文とともに本文照合へ渡す評価用リクエストで検出率を測る。通常CLIは入力ノートの照合専用モードを持たないため、これには別の承認済み評価ハーネスが必要。劣化例のmajor検出数/劣化例数に加え、正常ノートへの誤指摘数を記録する。
4. 「条件→操作→具体例をノートだけで追えるか」「見出しのまとまり」「表の必要性」を方式名を伏せて人手比較する。判定根拠と対応する原文IDを記す。
5. レポートの工程回数・実試行数と実行時間を記録する。費用は使用モデル・API使用量と評価時点の公式料金で算出する（現CLIはトークン使用量の集計を未実装）。トークン量を確認できなければ推定料金を実測値と扱わない。

暫定合格基準：重大な欠落・意味変更・不明語の断定・根拠のない補完が0、必須6項目がすべて保持され、復習に必要な手順と例を追えること。品質・費用・時間の改善は複数回の比較後に判断する。この短い評価セットだけで一般講義の品質を保証しない。

## 残る評価対象

分割をまたぐ定義と例、別概念・矛盾、長時間講義の中盤、情報が多い非手順型講義、台帳の抽出過多、同モデルの誤り共有を次の評価セットへ追加する。意味分割・全体構成・本文ブロック化はT-30/T-31で扱う。
