# 実教材テスト（T-33）

実装とオフライン検証を終えた後、利用者が生成品質を評価する手順。実APIは従量課金で、講義の文字起こしと派生した台帳・章構成・本文・指摘をGeminiへ送る。MP4/WAVは送らない。実行前に教材の加工とAPIへのテキスト送信の権利・利用条件、機密情報、使用モデルの料金とクォータを確認する。エージェントは実教材・実APIを実行していない。

## 最初に使う素材

最初は5〜10分程度で、条件のある手順、変数の更新、具体例、不明な用語などが含まれる原文を使う。原文を音声と照合し、認識誤りとノート生成の問題を分ける。原文と音声の対応はそのまま残す。

既存の`.transcript.md`または`.transcript.failed.md`があればそれを使う。新しく文字起こしする場合は、先に`elconv "C:\教材\講義.mp4" --no-article --output-dir "C:\教材\原文"`を実行する（API不使用、ローカルでWhisperモデルの取得が必要な場合あり）。記事の品質比較は同じ原文と同じGeminiモデルで行う。

## 実行例（PowerShell）

プロジェクトで仮想環境を有効にし、READMEの導入とキー設定を済ませる。APIキーをコマンド引数や記録表へ書かない。以下のパスは自分の教材へ置き換える。評価出力はリポジトリ外へ保存する。

```powershell
$source = 'C:\教材\原文\講義.transcript.md'
$evaluationRoot = Join-Path 'C:\教材\評価' (Get-Date -Format 'yyyyMMdd-HHmmss')
elconv $source --from-transcript --output-dir (Join-Path $evaluationRoot '通常')
elconv $source --from-transcript --note-pipeline --max-api-calls 40 --output-dir (Join-Path $evaluationRoot '台帳方式')
```

旧品質確認方式とも比較する場合は、追加の課金を確認したうえで次も実行する。

```powershell
elconv $source --from-transcript --quality-check --output-dir (Join-Path $evaluationRoot '旧品質確認')
```

最初は`--overwrite`を付けず、新しい評価フォルダを使う。再試行するたびに同じAPI費用が発生し得る。保存が失敗した場合は、原文と既存記事を確認してから別の出力先で再実行する。`--max-api-calls 40`は40工程で停止する上限であり、金額の上限ではない。通信再試行は各工程最大3試行。上限で停止した場合、品質が不合格だった場合、レポートだけが保存される場合がある。CLIの終了コード0で記事保存の成功を確認する。

抽出窓W、生成単位Jでは通常`2W+1+2J+max(J-1,0)`工程、すべての本文で修正すれば`2W+1+4J+max(J-1,0)`工程。W=J=1なら5〜7工程。分割数が増えると費用も増える。APIの一時障害以外の形式不正は自動再送信しない。

## 見る箇所

1. 原文の重要事項を人手で先に10件程度選ぶ。台帳が選んだ事項だけを評価対象にしない。定義・前提・理由・入力/初期値・条件・更新順・停止・例・例外・不明箇所から、教材に存在するものを選ぶ。
2. 各方式で、重要事項が正しく残ったか、ノートだけで例を追えるか、原文にない補完や不明語の断定がないかを照合する。
3. 見出しの粒度、講義の順番、定義と具体例のまとまり、表と手順の読みやすさを確認する。長い教材では原文分割の前後、章の境界、中盤も確認する。
4. 台帳方式の`.quality.md`で元のS番号（原文順）、P番号（長い発話の断片）、時刻と0始まりの文字範囲を確認する。`C0001.F001`は抽出窓1のF001。`jobs`の`block_mapping`を通じて章・本文ブロックと根拠を照合できる。原文ファイルへIDは書き戻さない。
5. `major`が妥当な指摘か、適切な留保を誤って不合格にしていないかを見る。レポートが合格でも、意味の正しさや欠落の完全検出は保証されない。
6. `observed_tokens`は取得できた分だけの合計。`usage_unknown_attempts_by_field`が0でない欄は完全な使用量ではない。`elapsed_seconds`はノート生成工程全体の時間で、文字起こし時間は含まない。実費はAPI管理画面等と照合する。

## 記録用テンプレート

以下を評価フォルダ内の任意のMarkdownへコピーする。教材本文や秘密情報をリポジトリへコミットしない。

```markdown
# ノート品質比較
実施日:
コミット（git rev-parse --short HEAD）:
モデル / プロンプト変更の有無:
教材の長さ / 原文と音声の照合状況:
API送信の利用条件を確認したか:

| 観点 | 通常 | 台帳方式 | 原文時刻・判断理由 |
| --- | --- | --- | --- |
| 必須事項の完全保持数 / 選んだ件数 | | | |
| 重要な欠落・意味変更の件数 | | | |
| 創作・不明語の断定の件数 | | | |
| 手順と具体例を追えるか | | | |
| 章構成・表・手順の読みやすさ | | | |
| 不合格になった指摘の妥当性 | | | |
| 工程数 / 実試行数 | | | |
| 処理秒数 | | | |
| 使用トークン取得分 / 不明試行数 | | | |
| 管理画面等で確認した費用 | | | |

改善が必要な箇所（時刻・症状・期待する説明）:
原文の誤認識が原因と思われる箇所:
```

暫定合格は重大な欠落・意味変更・創作・不明語の断定が0で、必要な手順と例を追えること。まず短尺で比較し、次に分割をまたぐ説明のある教材で再評価する。評価結果に応じて境界候補・章構成・抽出過多・モデルの検出性能を調整する。リモート同期・マージは利用者の認可後に行う。
