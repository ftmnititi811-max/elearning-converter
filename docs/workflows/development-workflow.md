# 開発の進め方

既存のプロジェクトルールと利用者の指示を、開発作業の流れに沿ってまとめた運用文書。ルールの追加や権限の拡大を目的としない。適用されるAGENTS.md、利用者の最新の指示、Gemini実行時の`.codex/GEMINI_POLICY.md`も確認する。

## 作業を始める

1. `git status --short --branch`で現在のブランチと未コミット変更を確認する。利用者の変更を勝手に戻したり、別の変更と一緒にコミットしたりしない。
2. [要件](../requirements.md)、[仕様](../spec.md)、[設計](../design.md)、[タスク](../tasks.md)を読む。
3. 問題の修正では[未解決問題](../issues/known-issues.md)と[検証記録](../verification.md)を参照し、確認済みの事実と仮説を分ける。
4. 実施範囲、検証方法、既存の許可を確認する。本文や機密情報を端末のログへ大量に出力しない。

## ブランチとコミット

| 対象 | 扱い |
| --- | --- |
| `dev` | 開発変更の統合先。利用者に許可されたマージを記録する |
| `codex/feat-*`等 | 機能開発・改修の作業ブランチ。新規ブランチの接頭辞は原則`codex/` |
| 既存のfeat | 作業が終わっても、削除の依頼なしに整理目的で削除しない |
| ローカルコミット | 利用者に許可済み。対象差分と検証結果を確認し、作業範囲のファイルだけを含める |
| push・リモート同期・マージ | その操作に対する利用者の明示的な認可を得てから実行する |

既存の作業ブランチがある場合は、その作業の継続か新規作業かを判断する。履歴を書き換える操作を、通常の整理やマージに含めない。マージは対象コミット・未コミット変更・競合を確認し、完了後にブランチと作業ツリーを再確認する。

## 動作を変える

更新順は、要件・受入基準 → 仕様 → 設計・タスク → 実装 → 検証。R/A/TのIDを対応付ける。

原文・記事の保存方式、APIへ送る内容、費用、利用条件を変える案は、具体化して利用者へ確認する。既に許可された範囲を毎回承認し直す必要はないが、許可を新しい送信先や有料機能へ拡張しない。

Python 3.11以降、Windowsの日本語・空白入りパスに対応する。外部コマンドは引数配列で呼び出し、プログラムからシェル経由で起動しない。

仕様を変えない文書の整理では、必要なファイルだけを編集し、リンクと記述の整合性を確認する。README等に別の編集予定がある場合は、利用者の指定に従って変更を避ける。

## オフラインで検証する

通常の自動テストは架空原文・合成データ・モックを使い、教材や実APIを使わない。

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
git diff --check
```

この環境では一時ファイルの権限に問題がある場合、既存の`.test-tmp`をTEMP/TMPに指定して検証している。必要な場合にだけ設定し、他の実行環境に必須とはみなさない。

テストの成功が示す範囲を記録する。API応答を固定したモックは、状態遷移・構造検査・保存保護を確認するもので、モデルによる意味の保持や欠落検出の実証にはならない。関連するチェックが成功した後は、新しい変更や未解決の懸念がなければ無目的に検証を繰り返さない。

## 実教材・Geminiを使う

実行前に`.codex/GEMINI_POLICY.md`を読む。利用者はエージェントによるノート生成・再生成・品質評価を許可しているが、実行は無料枠内に限定される。無料枠の状態・対象モデル・利用状況を確認できず、その条件を判断できなければAPIを呼ばない。

実教材での比較は[実教材テスト手順](../user-material-test.md)、評価方法は[比較評価手順](../note-pipeline-evaluation.md)を参照する。新方式の評価では実行コマンドと出力を確認し、`--note-pipeline`と旧`--quality-check`を混同しない。

台帳方式は429で即停止し、SDK内部の再試行を禁止する。他の一時障害も実試行数と使用量を考慮する。工程数の上限を、トークン量や料金の上限として扱わない。無料枠不足や同じ検査失敗を、別キーへの切替や無計画な再送で回避しない。

## データと結果を守る

- 元MP4と入力原文を変更しない。既存出力の置換には`--overwrite`を要求し、不完全記事を完成品として保存しない。
- キーは既存の`GEMINI_API_KEY`設定経路で読み、コード・ログ・記事・テスト素材・コミットへ記録しない。
- MP4/WAVをAPIへ送信しない。承認済みの文字起こしと派生データの範囲を維持する。
- 教材原文・生成ノート・教材由来の品質レポート・レビューはGit管理外の教材管理場所へ保存する。リポジトリ内の`learning_texts/`はそのための除外先であり、テスト用fixtureへ教材を複製しない。
- ステージ前後に対象ファイルを確認する。教材を含むディレクトリへ無差別に`git add`を実行しない。

## レビューと引渡し

授業ノートのレビューには`$review-lecture-notes`を使える。ユーザー共通のSkillとして導入されており、このリポジトリだけを取得した環境には含まれない。Skillを利用できない環境では、比較評価手順を参照し、原文の重要事項とノートの主張を双方向に照合する。

レビューだけの依頼では、追加の生成や外部送信は行わない。本文が生成されなかった場合は、文章品質を想像で採点せず、停止工程・固定の理由・未評価の範囲を整理する。

引渡しでは変更内容、検証結果、未解決問題、コミット、現在のブランチを伝える。動作変更の進捗はタスク、再現と結果は検証記録、未解決の影響と次の検証は未解決問題へ記す。参照先の全体像は[文書案内](../guides/documentation-map.md)にまとめる。
