# 要件定義

目的：利用権限のあるMP4講義の音声を、Windows向けPython CLIで復習用Markdownに変換・ローカル保存する。FFmpegで音声抽出、faster-whisperで文字起こし、Gemini APIで記事化する。映像・字幕・スライド解析、話者分離、GUI、一括処理はMVP対象外。

## 要件と受入基準

授業ノートの情報保持（R-18 / A-18、A-19 / T-24、T-25）：話題の網羅だけでなく、原文を根拠に処理や説明を追えることを目標とする。原文にある入力・初期値・条件・更新順序・終了条件・出力と、理解に必要な具体例・トレースを保持する。別概念の定義を混同せず、不確かな用語・式・数値を本文で確定事項として扱わない。確認できる説明は残し、不明部分のみ時刻付きの確認事項へ分離する。根拠時刻は目次ではなく実際の説明に対応させる。

受入基準：架空の時刻付き原文と期待ノートを照合し、上記の情報が保持されること、原文にない手順・数式の補完がないことをレビューできる。既存のAPI・表示経路で期待ノートが欠落せず扱えることをオフライン検証する（A-18）。モデルの実生成品質は別途承認された実API評価で確認し、モック成功とは区別する（A-19）。

| ID | 要件 |
| --- | --- |
| R-18 | 原文で確認できる手順・必要な具体例・概念の区別を保持し、不確かな語や式を断定せず、実際の説明箇所の時刻を付ける。詳細と受入基準は上記の情報保持方針に従う。 |
| R-01 | CLIでMP4と出力先を指定。欠落・非MP4は理由付きで終了。 |
| R-02 | ffprobeで音声を検査し、FFmpegでモノラル16 kHz WAVへ抽出。 |
| R-03 | 日本語を既定にfaster-whisperで時刻付き認識。空結果は失敗。 |
| R-04 | APIで講義の流れに沿う授業ノートを生成。理解に必要な前提・理由・具体例を残し、用語は文脈で説明する。定型的な前置きや重複を省き、見出し・表は整理に役立つ場合だけ使う。段落末・箇条書き末などの不要な句読点を省き、文の境界や誤読防止に必要なものは残す。根拠時刻を保持し、音声にない補完・断定を避ける。不明点は要確認事項へまとめる。 |
| R-05 | UTF-8の <stem>.md と <stem>.transcript.md を保存。元MP4は変更しない。 |
| R-06 | 既存出力は --overwrite 時のみ置換。不完全記事を完成品として残さない。 |
| R-07 | Gemini APIキーは環境変数 `GEMINI_API_KEY` から読み、未設定時はプロジェクトルートの `.env` にある同名の値を読む。環境変数を優先し、キーと本文をログへ出さない。 |
| R-08 | 処理段階と失敗理由をCLIに示す。 |
| R-09 | --no-article はAPIキーなしで原文だけ出力。 |
| R-10 | 記事化失敗時は時刻付き原文を救済名で保存し、部分成功を明示する。既存ファイルは `--overwrite` なしで変更しない。 |
| R-11 | 文字起こし失敗時は失敗した段階と内部例外の種類を示し、キー・本文・入力内容を表示しない。 |
| R-12 | FFmpegで作成した16 kHzモノラルPCM WAVはPyAVの音声デコーダーを介さずに読み、faster-whisperへ渡す。 |
| R-13 | Gemini呼び出し失敗時はHTTPステータスと例外種別を安全に表示し、一時的な障害だけを上限付きで再試行する。キー・本文・生の例外メッセージは表示しない。 |
| R-15 | 正式名称・配布名を `elearning-converter`、短縮コマンドを `elconv`、Pythonパッケージ名を `elearning_converter` に統一する。READMEとCLIヘルプも同じ名称を使用する。 |
| R-14 | 既定のGeminiモデルは利用可能な現行モデルを指定し、モデル名と費用の確認方法をCLI・READMEに示す。モデル指定オプションは維持する。 |
| R-16 | 記事化プロンプトをプロジェクト直下の `prompts/article.md` に外部化し、Pythonを編集せずに変更できる。R-04の授業ノート形式を指示し、文字起こしだけを資料として送る方式を維持する。 |
| R-17 | 記事応答のJSON構造をAPI設定でも指定する。応答失敗は分割番号と固定の理由（生成打切り・ブロック・空応答・JSON構文・項目型・時刻形式）で識別し、キー・本文・生のAPIメッセージを表示・保存しない。不完全応答を記事として採用せず、形式不正の自動再送信は行わない。 |

Windows 11、Python 3.11以降、CPU環境を基準としFFmpegは別途導入。MP4/WAVは外部送信せず、記事化時に文字起こしテキストだけGemini APIへ送る。従量課金を明示する。教材の加工・共有は著作権と利用条件に従い、機密情報があればAPI送信前に確認する。記事は復習用下書きで、原音声と照合する。

仮定：日本語の音声付きMP4。モデル、分割長、再試行、記事の長さ、救済名は暫定値を仕様に記し、権利確認済み短尺講義で品質・時間・費用を評価する。料金上限、専門語・数式の精度目標は実測後に決める。実APIテストは課金のため実施前に利用者へ確認する。

## R-19 既存文字起こしの記事化

`--from-transcript`でelconvの時刻付き原文Markdownを入力し、音声処理なしで記事だけを生成する。入力原文を変更せず、失敗時も原文を保持する。A-20で入力検証・音声処理省略・上書き保護・API失敗を確認する。

## R-20 品質確認モード（A-21 / T-27）
`--quality-check`で重要事項を含めて生成し、独立照合、問題がある場合の1回の修正、再照合を行う。原文と生成ノート・重要事項・指摘をGeminiへ送る。重大な問題が残れば記事を確定せず既存記事を保持する。品質レポートをローカル保存する。MP4/WAVは送らない。通常モードの送信・呼出し回数は維持する。
受入：通常2回・修正時最大4回/分割、未解決重大問題・不正応答・通信失敗の保存制御、入力保護、分割の文脈と本文対象の区別、秘密情報非表示をオフラインで検証する。モデルの検出能力は実API評価まで未確定とする。

## R-21 根拠付き情報台帳（A-22 / T-28）
採用された品質改善案の第1段階。`--note-pipeline`で原文へのID付与、本文とは独立した情報抽出、台帳と原文の独立照合、本文生成、本文と原文の双方向照合を行う。すべての対象原文に情報の根拠または除外理由が必要で、すべての台帳情報を本文に対応付ける。IDの対応検査は意味の正しさの保証とは区別する。
送信は文字起こしと派生した台帳・章構成・本文・指摘のみでMP4/WAVを含めない。台帳と根拠ID・本文との対応を既存の品質レポートに保存し、別の中間ファイルは作らない。通常モードと既存品質モードは維持する。台帳照合でmajor、本文の再照合でmajor、不正応答・通信失敗では記事を確定しない。第1段階の4/6回は章構成追加後には適用せず、完成方式の回数はR-23〜25/動作仕様に従う。
A-22：架空原文で同時刻・長いセグメント・分割越しのID一意性、原文の未処理、未知/重複ID、台帳の未掲載、参照外根拠、不正な型、工程上限と修正回数、台帳不合格の早期停止、修正時の情報保持、後続分割失敗、入力・既存出力保護、レポート失敗・秘密非表示をオフライン検証する。

## R-22 品質評価セット（A-23 / T-29）
人手で定めた必須事項と根拠、条件・具体例・不明語を含む架空原文、正常ノートと意図的に劣化したノートを評価セットに持つ。人手による情報保持・忠実性・可読性評価とAPI工程回数・時間・費用を比較できる手順を記す。A-23は期待情報と実装の経路検証を確認し、実モデルの欠落検出性能は別途承認された実API評価まで未評価とする。

## R-23 講義全体の構成（A-24 / T-30）
台帳方式では抽出窓の末尾付近で話題転換・文末・開始時刻間隔を優先し、全窓の台帳照合後に全情報の章構成を別APIで計画する。章は講義順を維持し、関連する定義・手順・例をまとめる。本文生成単位は原文の文字数上限で再分割し、抽出窓と独立させる。隣接する本文間も原文を根拠に照合し、重大な問題が残れば保存しない。
A-24：境界選択、全原文の一意な所属、章構成での未知/重複/欠落/逆順情報の拒否、窓をまたぐ章、本文対象と文脈の区別、最終境界照合の保存制御を架空データで検証。意味によるまとまりの妥当性は実教材で人手評価する。

## R-24 構造化本文（A-25 / T-31）
台帳方式の本文を段落・箇条書き・番号付き手順・表・コードのブロックとして取得し、PythonでMarkdownへ整形する。全ブロックの根拠ID・情報IDを検査し、表の列数不一致や不正なブロック構造を拒否する。空セル等を推測で補完しない。通常/既存品質モードの表示は維持。
A-25：各ブロックの表示、改行・区切り文字・コードフェンスを含む内容、根拠時刻の独立表示、表の構造不正、修正による情報欠落をオフライン検証する。

## R-25 実教材テストへの引渡し（A-26 / T-32）
台帳方式のAPI工程上限（既定100、通信再試行別）をCLIで指定でき、上限に達したら追加送信せず記事を確定しない。既存品質レポートに章構成、対応、段階別の工程数・再試行数・処理時間、API使用トークン数と取得不能の有無を記録する。料金を自動推定して実費と扱わない。権利確認済み原文で既存方式と比較する手順と記録用テンプレートを用意する。実API・実教材の評価は利用者が実施する。
A-26：上限の事前引数検証・到達時の停止、使用量の欠落/不正値、失敗時のレポート・記事保護、CLI経由の模擬全工程を検証する。同期・マージは利用者の認可まで実施しない。

## R-26 無料枠のクォータ到達時停止（A-27 / T-34）
台帳方式は429を受けたら再試行せず停止し、以降の工程を送信しない。SDK内部の再試行を無効化し、他の一時障害だけアプリ側で最大3試行する。無料枠・利用残量の確認は.codex/GEMINI_POLICY.mdに従う。これだけで課金状態や残量を保証しない。
A-27：モックと実SDKのローカルHTTP transportで429が1試行に限られ、未合格となり既存記事を保持することを検証する。

R-27 / A-28 / T-35：台帳方式の形式不正は、項目キー、ID型/空配列、未知ID、重複ID、根拠集合不一致、必須情報未掲載、ブロック種別ごとの欄不正を固定文で区別する。本文・モデル由来の値はエラーへ含めない。ローカルで原因分類と秘密非表示を検証する。
抽出/本文応答のID選択肢をリクエストごとのJSON Schemaのenumでも制限し、対象外IDの生成を抑える。ローカル検査は維持する。
